# Household Electricity RNN: Final Project Report

## 1. Executive summary

This project forecasts the next hourly value of `Global_active_power` for one
household using a vanilla recurrent neural network (RNN). The data pipeline
aggregates the original minute-level UCI household electricity data into
hourly observations, scales using training-period values only, creates
chronological sliding windows, and evaluates predictions on an untouched test
period.

The final practical baseline uses 24 previous hours, 7 input features, and 32
hidden units. The PyTorch and TensorFlow/Keras implementations give very
similar results:

| Implementation | Test MAE (kW) | Test RMSE (kW) | Test R² |
|---|---:|---:|---:|
| PyTorch | 0.3916 | 0.5179 | 0.4939 |
| TensorFlow/Keras | 0.3976 | 0.5205 | 0.4887 |

The NumPy implementation was intentionally designed as a transparent
mathematical reference. Its locked two-epoch SGD result is substantially
worse:

| Implementation | Optimizer | Epochs | Test MAE (kW) | Test RMSE (kW) | Test R² |
|---|---|---:|---:|---:|---:|
| NumPy reference | SGD | 2 | 0.6991 | 0.8105 | -0.2395 |
| NumPy longer experiment | SGD | 20 | 0.4883 | 0.5985 | 0.3241 |
| PyTorch practical model | Adam | 11 best epoch | 0.3916 | 0.5179 | 0.4939 |
| TensorFlow/Keras practical model | Adam | 6 best epoch | 0.3976 | 0.5205 | 0.4887 |

The negative NumPy R² is therefore primarily an undertraining and optimizer
comparison issue, not evidence that NumPy implements different RNN
mathematics.

## 2. Project objective and data pipeline

The objective is one-hour-ahead forecasting of household active power:

```text
minute-level UCI readings
  -> R cleaning and hourly aggregation
  -> training-only min-max scaling
  -> chronological sliding-window sequences
  -> vanilla RNN
  -> inverse scaling to kW
  -> evaluation on unseen test sequences
```

The locked sequence contract is:

- Input shape: `(samples, 24, 7)`
- Target shape: `(samples,)`
- Training period: 27,647 sequences before the validation split
- Training subset: 24,882 sequences
- Validation subset: 2,765 sequences
- Unseen test set: 6,894 sequences
- Hidden units: 32
- Batch size: 64 for the practical implementations
- Learning rate: `0.001`
- Seed: 42
- Chronological split and no shuffling

The original target values in the test set range from approximately `0.1604`
to `5.6268 kW`, with a mean of approximately `1.0025 kW`.

## 3. Mathematical model

For each timestep, the RNN updates its hidden state using:

```text
a_t = W_xh x_t + W_hh h_(t-1) + b_h
h_t = tanh(a_t)
```

After the final timestep, the output layer predicts the next hour:

```text
y_hat = W_hy h_T + b_y
```

The NumPy reference computes these equations explicitly and performs
backpropagation through time (BPTT). Its analytical gradients are checked
against finite-difference numerical gradients. PyTorch and TensorFlow/Keras
use automatic differentiation for the same recurrence.

The 24-hour, 7-feature, 32-unit model has:

```text
32*7 + 32*32 + 32 + 1*32 + 1 = 1,313 trainable parameters
```

The small hand-calculated explanation is available in
[`docs/03_RNN_MATHEMATICS.md`](../docs/03_RNN_MATHEMATICS.md), and the
visual example is generated by
[`models/rnn/rnn_math_example.py`](../models/rnn/rnn_math_example.py).
Visualizations from the trained model and real held-out examples are described
in [`rnn_tensorflow_real_examples.md`](rnn_tensorflow_real_examples.md).

## 4. Why the R² is moderate rather than close to 1

The best practical R² is approximately `0.49`. This means the model explains
about 49% of the variance in the unseen test target relative to a mean-value
predictor. It is not a negative result, but it shows that a simple vanilla RNN
does not explain all household demand variation.

The main causes are:

### 4.1 Unpredictable household behavior

Appliance switching, cooking, heating, washing, and occupancy changes can
produce demand changes that are not determined by the previous 24 hours.

### 4.2 Missing explanatory variables

The model does not explicitly receive weather, temperature, occupancy,
holiday, calendar, appliance-state, or electricity-price information. These
variables could explain changes that past power readings alone cannot predict.

### 4.3 Extreme peaks are difficult

The test target ranges up to approximately `5.63 kW`, while the practical
models predict up to approximately `3.97 kW` for PyTorch and `3.71 kW` for
TensorFlow/Keras. The model captures the normal level but smooths many sudden
peaks. Missing peaks creates large squared errors and reduces R².

### 4.4 Vanilla RNN memory limitations

The tanh recurrence can suffer from vanishing gradients over long sequences.
The model may not preserve all useful information from earlier timesteps,
especially when the relevant pattern is longer or irregular.

### 4.5 R² is sensitive to large errors

R² is based on squared residuals. A small number of large peak errors can
strongly reduce R² even when MAE appears reasonable. This is why MAE, RMSE,
R², prediction-range plots, and residual plots must be interpreted together.

## 5. Why the two-epoch NumPy R² is negative

R² is defined as:

```text
R² = 1 - SSE_model / SSE_mean
```

where `SSE_mean` is the squared error obtained by always predicting the
average target. If the model is worse than that baseline, then
`SSE_model > SSE_mean` and R² becomes negative.

The two-epoch NumPy model predicted only approximately:

```text
1.35 kW to 1.57 kW
```

while the actual test values ranged from approximately:

```text
0.16 kW to 5.63 kW
```

Its predictions were concentrated near the center and failed to reproduce
both low-demand periods and high-demand peaks. Consequently, its RMSE was
`0.8105 kW`, worse than the mean-prediction reference, producing
`R² = -0.2395`.

This was not a mathematical failure of the NumPy RNN. The NumPy model used
plain SGD for only two epochs because its purpose was to expose forward
propagation, loss, BPTT, and gradient checking clearly. It was not trained
under the same practical optimization setup as the other two models.

The controlled longer NumPy run confirms this explanation:

| NumPy training duration | Test RMSE (kW) | Test R² |
|---:|---:|---:|
| 2 epochs | 0.8105 | -0.2395 |
| 20 epochs | 0.5985 | 0.3241 |

Training longer expanded the prediction range and substantially improved
generalization, although SGD still did not reach the Adam results.

## 6. PyTorch versus TensorFlow/Keras versus NumPy

### NumPy

**Role:** mathematical reference implementation.

- Explicit forward propagation
- Explicit loss calculation
- Manual BPTT
- Numerical gradient checking
- Plain SGD
- Best for teaching the equations and verifying correctness
- Slow and less convenient for production training

### PyTorch

**Role:** practical neural-network implementation.

- Uses `nn.RNN` and `nn.Linear`
- Uses automatic differentiation
- Uses Adam
- Uses mini-batches and early stopping
- Achieved the best measured result in this project:
  `RMSE = 0.5179 kW`, `R² = 0.4939`

### TensorFlow/Keras

**Role:** high-level practical implementation.

- Uses `tf.keras.layers.SimpleRNN` and `Dense`
- Uses automatic differentiation
- Uses Adam
- Uses mini-batches and early stopping
- Achieved nearly the same result as PyTorch:
  `RMSE = 0.5205 kW`, `R² = 0.4887`
- Provides a concise model definition and convenient `.keras` checkpoint

The small PyTorch advantage is not evidence that PyTorch is universally
better. Differences can come from initialization details, framework
implementation details, optimizer trajectories, and early-stopping epochs.
The results show that both frameworks reproduce the same practical behavior.

## 7. Fairness of the comparison

The PyTorch and TensorFlow/Keras results are the fairest direct comparison:
they use the same input shape, hidden size, Adam learning rate, batch size,
seed, chronological validation split, patience, and untouched test set.

The two-epoch NumPy result should not be compared as an equally optimized
competitor because it uses plain SGD and much less training. The 20-epoch
NumPy run is a more informative comparison, but it still uses a different
optimizer and training procedure.

The correct conclusion is:

> NumPy verifies the RNN mathematics. PyTorch and TensorFlow/Keras provide
> practical optimized training. Their similar scores show that the
> mathematical architecture is consistent across implementations.

## 8. Controlled experiments

### Hidden units

The practical hidden-unit experiment kept the other controls fixed:

| Hidden units | Parameters | Test RMSE (kW) | Test R² |
|---:|---:|---:|---:|
| 16 | 401 | 0.5414 | 0.4470 |
| 32 | 1,313 | 0.5179 | 0.4939 |
| 64 | 4,673 | 0.5307 | 0.4685 |

Thirty-two units performed best among the tested choices. This is a result
for this dataset and experiment, not a universal rule.

### Sequence length

| History length | Test RMSE (kW) | Test R² |
|---:|---:|---:|
| 6 hours | 0.5505 | 0.4286 |
| 12 hours | 0.5261 | 0.4784 |
| 24 hours | 0.5179 | 0.4939 |
| 48 hours | 0.5268 | 0.4729 |

Twenty-four hours performed best among the tested contexts. Increasing the
history to 48 hours did not improve generalization, possibly because the
vanilla RNN had more information to process without gaining useful long-range
memory.

## 9. Interpretation of prediction and error graphs

The residual is:

```text
error = actual - predicted
```

- Error near zero indicates an accurate prediction.
- Positive error means underprediction.
- Negative error means overprediction.
- Large spikes indicate sudden or unusual consumption.

The residual plots are broadly centered around zero, so there is no severe
overall directional bias. However, the spikes show that the model struggles
with sudden demand changes. The model tends to smooth extreme values, causing
underprediction at high peaks and occasional overprediction at low values.
This behavior explains the moderate R² and the gap between MAE and RMSE.

## 10. Limitations and future improvements

The current model is a sound vanilla-RNN baseline, but it is not intended to
be the final state-of-the-art forecaster. Improvements could include:

1. LSTM or GRU cells for better long-range memory.
2. Weather, calendar, occupancy, and appliance-level features.
3. Hyperparameter tuning for learning rate, hidden size, and batch size.
4. A peak-aware or weighted loss to penalize missed demand spikes.
5. Multi-step validation and rolling-origin evaluation.
6. Prediction intervals to communicate uncertainty.
7. More advanced CNN-RNN or Transformer architectures.

## 12. Final conclusion

The project successfully demonstrates the complete path from RNN mathematics
to practical forecasting. The NumPy implementation is valuable because it
makes the recurrence, loss, BPTT, and gradient checks visible. PyTorch and
TensorFlow/Keras are better suited to practical training because Adam,
automatic differentiation, batching, and early stopping produce substantially
better results.

The final practical R² of approximately `0.49` should be interpreted as
moderate predictive performance for a simple model with limited input
information. The model learns meaningful daily and short-term temporal
patterns, but unpredictable household behavior and sharp consumption peaks
prevent it from explaining all variance. The results are therefore
consistent with the expected limitations of a vanilla RNN on household
electricity forecasting.
